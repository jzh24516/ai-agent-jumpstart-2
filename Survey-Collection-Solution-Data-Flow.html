Step 3 · Azure ingress boundary

Public HTTPS ingress with two explicit Origin checks

1

Azure platform CORS

App Service answers browser preflight only for the configured origins.

  • GitHub Pages origin
  • localhost:5173
  • 127.0.0.1:5173
2

Application Origin check

The Function reads Origin and rejects any non-allowlisted value with 403 ORIGIN_NOT_ALLOWED.

3

Method boundary

OPTIONS returns 204, POST enters processing, all other methods return 405.

Why the HTTP trigger is anonymous

GitHub Pages has no server identity. The endpoint therefore uses anonymous Function auth and compensating controls: exact CORS allowlist, signed workshop claim, strict schema validation, request size cap, durable rate limiting, and no direct database credential.

Security nuance

CORS is a browser control, not authentication; callers without an Origin header are not blocked by it. The survey token proves workshop-claim integrity, not participant identity. Abuse resistance comes from validation, managed-identity service boundaries, and rate limiting.

Step 5 · Azure Table rate limiter

Count distinct submissions without storing raw client IP

Entity key design

PartitionKey = YYYYMMDDHH + "-" + base64url(HMAC-SHA256(clientAddress, signingSecret))[0:32] RowKey = submissionId

A user-assigned managed identity authenticates to the private Table endpoint; no storage key is used.

Decision algorithm

  • Create an entity for this client-hour + submission ID
  • A 409 conflict means this is the same retry; continue
  • Count rows in the partition
  • Allow up to 120 distinct submissions per hour
  • Return 429 + Retry-After: 3600 above the limit

Step 6 · Service-to-service handoff

Forward normalized JSON to a protected HTTPS callback

1PrepareNormalized body only
2CorrelateX-Correlation-ID = submissionId
3Attempt 120-second timeout
4Wait 250 msOnly transient failures
5Attempt 2Then wait 500 ms
6Attempt 3Final outcome

Retry

Network/timeout exceptions, HTTP 429, and HTTP 5xx responses. Every attempt carries the same submission ID.

Do not retry

Other HTTP 4xx responses indicate a contract or authorization problem. The loop stops immediately.

Secret, not Private Link: SURVEY_FLOW_URL is a Key Vault reference and never reaches the browser, source, or logs. Flex routes the runtime call through VNet-integrated egress to the Power Automate trigger's public HTTPS endpoint; no Function-to-Flow Private Endpoint exists.

Return

Step 9 · Return path

Success means Dataverse finished, not merely "request accepted"

1

Flow ACK

After both upserts, Flow returns:

HTTP 200 { "ok": true, "submissionId": "..." }
2

Gateway ACK

The Function treats any HTTP 2xx Flow response as stored, logs the submission ID, and returns its own matching 200 ACK.

3

Browser commit

The UI shows Thanks and saves a local feedback receipt only after ok = true and exact ID equality.

Browser layer

One UUID per modal session; retry reuses it.

Limiter layer

Duplicate RowKey conflict is accepted and not counted twice.

Persistence layer

GUID row IDs update the same Workshop and Survey Response.

Net effect: retries can safely cross browser, Function, and Flow boundaries without creating duplicate survey rows.
